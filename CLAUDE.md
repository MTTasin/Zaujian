# Zaujain Nikah Point — Ecommerce + Configurator + AI Salesbot

Custom ecommerce for a Bangladesh business selling premium customized Nikah Nama products (books, box, pen, mirror, dupatta, thumb, frames, combos). Two apps in the repo: `backend/` (Django) and `frontend/` (Next.js). Full original spec: `zaujain_ecommerce_build_plan.md` (§15 = locked decisions). This file reflects the current built state.

## Audience — read before any customer-facing work
Non-technical people across Bangladesh incl. remote villages. Slow 2G/3G, low-end Android, low literacy.
- **Bengali only** on storefront. Terms: combo (not set), premium pen, মিরর (not আয়না).
- **Image-first, minimal text. Huge tap targets. Mobile-first. Low bandwidth** (compress + lazy-load, thumbnails not 50 full inline images).
- **Live price always visible** while configuring.
- **Admin panel is English**, technical — opposite audience.

## Tech stack
- Frontend: Next.js 16 (App Router, TS, Tailwind v4), `frontend/`. **Premium-editorial design system** (light theme): plum/rose/gold on warm cream; tokens in `globals.css` via Tailwind v4 `@theme inline` (no config file). Fonts: Noto Serif Bengali (headings, `font-display`) + Hind Siliguri (body, `font-sans`). The brand gradient (`.brand-gradient` / `.brand-gradient-text`) is now a **rose→plum accent**, not the whole identity. Shared UI primitives in `src/components/ui/`, site shell in `src/components/shell/` (SiteHeader/SiteFooter/MobileTabBar), live preview at `/ui-kit`. Charts via `recharts`.
- Backend: Django 6 + DRF, `backend/`. Single app `app`.
- DB: SQLite dev / PostgreSQL prod via `DATABASE_URL` (`dj-database-url`). Never hardcode.
- Media: Django local media folder. `next/image` is `unoptimized: true` (cPanel has no optimizer; still lazy-loads). Upload pre-sized images. **Orphaned-file cleanup**: `django-cleanup` (INSTALLED_APPS, last) auto-deletes the old file whenever an `ImageField`/`FileField` is replaced or its row deleted; the `purge_orphan_media` management command (cron) sweeps `MEDIA_ROOT` for any file no DB row references (backlog + safety net for bulk `.update()`).
- Redis (128MB) = cache/sessions only, **NOT a job queue** (there is no worker process to consume one). Wired in `settings.py` on `REDIS_URL`: set → `RedisCache` + cache-backed sessions; unset → `LocMemCache`, and everything still works.
- Hosting: shared cPanel + Passenger. **No Docker, no background workers.** Real-time = polling, never websockets.

## Hard constraints
- **Money = `DecimalField`, never float.**
- **No job queue.** Fraud check + DeepSeek calls run synchronously with timeouts + fallbacks.
- **Snapshot prices** into cart/order at add-time; later admin edits don't mutate placed orders.

## Products & pricing
- `Product.kind` (behavior, drives configurator + pricing): `layered` (color+corner+center, e.g. book/box), `gallery` (pick one design, e.g. pen/mirror), `dupatta` (lace+lines lookup), `simple` (buy as-is or pick one design). `category` = free-text internal grouping (storefront listings carry their own `PrebuiltCombo.category`). Add unlimited product types from the panel — no code.
- Pricing engine `app/services/pricing.py`: base + option modifiers; dupatta = direct lookup; `price_bounds()` gives min/max for the "price range" step.
- **Price conflicts — customization wins (locked).** For `kind=dupatta` the option price (lace+lines) is **absolute**, so `base_price` is ignored by design: set base 1600 + an option at 1500 and everything quotes **1500**. This is consistent across surfaces — storefront shows `min_price` for any customizable product (never `base_price`), and `_shop_facts` feeds the bot the same number. `base_price` only ever renders for non-customizable products. The admin edit form warns that base_price is ignored for dupatta. (For layered/gallery/simple, options are modifiers *on top of* base_price — no conflict possible.)
- `ConfigurationImage`: a real photo for a specific color+corner+center combo — shown instead of stacked overlays when the customer's pick matches.
- **PrebuiltCombo** + `ComboImage` (multi-image) = **the catalogue model**. Every buyable listing on `/products` is one: a bundle when it links several Products, a **single item when it links one**. Tapping → Add to cart OR "Make changes" (opens wizard preloaded with the linked products). `PrebuiltCombo.category` (free text) drives the card badge and the `/products` filter — without it the card falls back to "কম্বো", which reads wrong on a single item. Plain Products are **not sold directly**; they are customizer building blocks.

## Customization rules (BUILT)
- **`Product.exclusive_group`** (admin free text, e.g. `nikahnama` on book/frame/thumb): products sharing a non-blank group can't be picked together. `/customize` **auto-swaps** (picking ফ্রেম drops বই) via the pure helper `lib/exclusive.ts` (`applyExclusive`, `exclusiveGroups`). The rule note ("বই / ফ্রেম / থাম্ব — যেকোনো একটি") is **derived from product names** — no hardcoded Bengali. Django `PrebuiltComboForm.clean()` blocks a combo mixing one group; `_shop_facts` tells the bot.
- **`Product.customize_order`** (admin) drives the picker + wizard order. The old hardcoded `ORDER` array is **deleted** (unknown categories used to sort to the top). The wizard inherits order via `sessionStorage.wizard_slugs`.
- **`ProductField`** (`product.input_fields`): admin-defined inputs asked during customization (label, placeholder, required, order) — e.g. বরের নাম, এখানে কি বসবে?. Managed per product in Admin → Products (only for non-`simple` kinds — plain items have no configurator to render them). Single-line text only.
- Answers + an always-available **optional note** ("বিশেষ নির্দেশনা") save into the existing `CartItem.config` JSON (`config["fields"]` = `[{label, value}]`, `config["note"]`) — no migration, and they inherit the price-snapshot guarantee. The **label is snapshotted next to the value**, so renaming a field never rewrites a placed order. `cart_add` **re-validates required fields server-side** (never trust the client) and caps values/note at 200 chars. `_config_display` renders them, so they appear in the cart AND the Orders admin automatically.
- Wizard has a **← পূর্ববর্তী** button (hidden on step 1). Shared configurator wiring = `useCustomerInputs(product)` hook (node/validate/payload) used by all 3 configurators.

## Customer flow
- Landing (hero + featured combos + sticky customize) → `/customize` (pick items, live **price range**) → `/customize/build` (sequential per-product configurator, confirm→next) → cart → checkout.
- **`/products` is the catalogue** — search (`?q=`) + category chips (`?category=`), listing every active PrebuiltCombo. **`/shop` and `/product/<slug>` retired**: both 308 to `/products` via `next.config.ts` redirects (query preserved). The floating customize CTA shows on **home/products/gallery only**.
- Book layered flow = 2 screens: cover (color+corner+center, live preview) then a **separate** large inside-page gallery.
- Checkout: cascading BD **Division→District→Thana** address (`frontend/src/lib/bdLocations`), WhatsApp field, email. Post-order shows "we'll call to confirm".
- **District-based delivery charge**: reduced charge for the home district (env `INSIDE_DISTRICT`, default `Chattogram` → `DELIVERY_CHARGE_INSIDE`, default 80; else `DELIVERY_CHARGE` 120). Computed **backend-authoritatively** at order create via `delivery_charge_for(district)` (`views.py`); `shop-info` returns both charges + inside district so checkout shows the right total live as district changes.

## Orders
- **`uid`** = 6-char public code; customers only ever see uid, never the numeric id. Track at `/track/[uid]` (+ `/track` to enter a code). Email at checkout + each status change includes the tracking link. The track-page **stepper starts at `confirmed`**; earlier states (`in_review`, legacy `pending_payment`) show via the status badge + the advance-payment form.
- **Order lifecycle — nothing auto-confirms (COD, review-first).** Every website order lands in **`in_review`**; an admin phones the customer, then **Confirm** (books Steadfast + fires the Meta Purchase) or **Cancel** (no Purchase — a declined order never reports a conversion). `advance_required` is now just a **mark** on the review (fraud <70 still asks for the advance), no longer its own landing status. Legacy `pending_payment` rows still exist and are handled everywhere `in_review` is.
- Cart/track thumbnail (`_resolve_preview`) resolves combo image → configured option image (color/config-photo/static/dupatta) → **falls back to the product's primary catalog photo** for as-is products (else the gift placeholder).
- Admin Orders: **guarded hard-delete** (only `in_review`/`pending_payment`/`cancelled`; backend enforces, others must be cancelled) + **search** (`?q=` over uid/name/phone/email) + **sorting** (`?sort=`).
- **Order list sorting** (backend-authoritative, `AdminOrderViewSet.SORTS` whitelist; unknown value → default): default `status` = **workflow priority** from `STATUS_PRIORITY` (`in_review` → `pending_payment` → `in_production` → `confirmed` → `shipped` → `delivered` → `cancelled`), tie-broken newest-first — reorder that one list to change the default. Other options: date, total (annotated `subtotal+delivery`, since `Order.total` is a property), customer, code, district, paid/unpaid, courier booked, repeat customers. Frontend labels in `ORDER_SORTS` (`adminApi.ts`) — a dropdown plus **clickable column headers** (click toggles asc/desc, ↑/↓ arrow); the choice persists in `localStorage.admin_orders_sort`. Tests: `app/tests/test_order_sorting.py`.
- **Status colour-coded order rows** (admin Orders list). One hue per status, walked round the wheel so no two neighbouring workflow states share a family: `in_review` orange · `pending_payment` yellow · `confirmed` blue · `in_production` violet · `shipped` cyan · `delivered` green · `cancelled` grey (the only greyed row — dead weight, dimmed, red rail; red therefore never competes with a live state). Each row also gets a 4px left rail in the saturated hue (colour alone is not an accessible signal) — the rail hangs off the first `<td>` because `box-shadow` on a `<tr>` is unreliable. Defined once in `globals.css` on a plain `[data-order-status]` selector (so the legend chips reuse the same vars), with a **separate deep palette for dark mode** — a pale wash dissolves into the `#151c28` admin surface. The list carries a colour **key** whose chips are also the status filter. Print forces rows back to transparent.
- **No per-order costing.** `Order.cost_price` / `Order.profit` were **deleted** (migration 0032) — money is business-wide now, in the **Finance cash-book** (own section below). A finance entry may be *marked* against orders, but nothing is allocated back, so no order carries a profit figure.
- **Edit a placed order's item config** (two actions, both preserve the price-snapshot philosophy per item): `edit_config` (`orders/{id}/edit_config/`) edits only the customer's **text** — `config["fields"]` values, the note, combo line values (options/price untouched, 200-char cap); `edit_item_options` (`orders/{id}/edit_item_options/`) changes the **color/design selection** and **reprices** via `pricing.price_selection` (merges option keys, keeps text answers, recomputes `subtotal`/COD). Option edit is customizable-**product** items only; combos-as-is stay text-only.
- **Manual (off-website) orders** — `orders/manual/`, page `/admin/orders/new`. A WhatsApp/Messenger/walk-in order is typed by hand but ends up shaped like a website order. Each line may: **link a real listing or product** (`orders/catalogue/` feeds a searchable picker of active PrebuiltCombos + Products with thumbnail, shop price and detail labels) — the FK gives the order its photo via `_resolve_preview` and keeps `edit_item_options` usable; and carry **any number of admin-typed details** (বরের নাম, তারিখ, ডাকনাম…) plus a per-item note, written into the **same `config["fields"]` / `config["note"]`** shape the storefront uses, so labels are snapshotted with values and every existing surface renders them for free. Picked lines prefill the linked item's own `ProductField`/`ComboField` labels. Price: the typed one always wins; blank falls back to `_catalogue_price` (combo price, else `price_bounds()` min so a dupatta quotes its option price, not `base_price`). A line needs only a title **or** a link. Caps mirror `cart_add` (200 chars, 20 details). Shared builder `_manual_line`/`_create_manual_items` is used by create **and** `edit`; `edit` with an **empty** items list now leaves the lines alone instead of wiping them, and the order-detail edit form round-trips each line's link + details so editing a title never drops them. Tests: `app/tests/test_manual_order.py` (17).
- **Repeat customer**: same phone as a prior order → greeted (track page + email), badge in admin.
- Fraud check decides advance only (not confirmation): aggregate success ratio **≥ `FRAUD_MIN_SUCCESS_RATIO` (70) → no advance**; else `advance_required` + manual bKash/Nagad step. No history / both couriers down → advance (safe default). Either way the order sits in `in_review` until an admin confirms.

## Couriers
- **Fraud check** (Steadfast + Pathao): `app/services/fraud_check.py`, ported from PHP `laravel-fraud-checker/`. Merchant-login creds from env. Raw response stored on Order. Sync, per-courier timeout, fallback = require advance.
- **Pathao no longer shares counts.** Their v2 `/user/success` answers `{"version":"v2","show_count":false,"customer_rating":"excellent_customer"}` — **no `customer` object**, so the old parser silently produced "0 delivered / 0 cancelled / 0%", which reads as *never ordered* rather than *not told*. Now each courier's stats carry **`counts_available`** (and Pathao a **`rating`** bucket): a courier without counts is **excluded from the aggregate** (folding its zeros in would halve a real history) and both UIs show the rating badge instead of zeros. The old `customer`-with-counts shape is still parsed if it ever returns; **`show_count: false` outranks a present `customer`** (a stub of zeros next to it would otherwise parse as a real "never delivered" history). Pathao's optional `risk_level` + `message` are carried through when sent and omitted when not. Buckets: `excellent_customer`, `good_customer`, `moderate_customer`, `risky_customer`, `new_customer` — documented only third-party, and the enum is Pathao's to change, so `lib/courierRating.ts` matches substrings and degrades unknown values to amber (rating) / slate (risk), never to green. Both admin surfaces render the grading through the shared `components/admin/CourierGrading.tsx`. **The advance decision is still counts-only** (in practice Steadfast-driven) — the rating deliberately does not influence it. Popular BD fraud-checker repos (`Fraud-Checker-BD-Courier-Laravel`, `kaderdevbd/fraud-checker`) hit the **same** endpoint and read the same `data.customer.*` fields — they get counts because of their *account*, not different code; theirs would report 0/0/0 on this account. Tests: `app/tests/test_fraud_check.py` (11) + `frontend/src/lib/courierRating.test.ts` (8).
- **Consignment booking**: Steadfast official API (`Api-Key`/`Secret-Key`), only on manual admin Confirm action. `cod_amount = subtotal + delivery − advance_received`. Store consignment_id + tracking_code. On fail: don't confirm, show error.
- **Multiple consignments per order**: the primary booking stays on `Order`; extra bookings live in `ExtraConsignment` rows (FK). `orders/{id}/book_extra/` books an ADDITIONAL consignment with a per-entry **editable** payload (recipient/phone/address/COD/item description, prefilled from the order) via `create_consignment(order, invoice, overrides=)`; unique invoice `{uid}-2/-3…`; `SteadfastError` → 502, no row. Order page has an "Additional consignments" card.
- **Consignment action parity (primary ⇄ additional)**: every consignment — primary and each extra — exposes Copy tracking, Print challan, Refresh status, Re-submit. Extras use `orders/{id}/extra_status/` + `orders/{id}/resubmit_extra/` (body `extra_id`); status-by-cid via `steadfast_order.get_status_by_cid`. Per-extra challan = `/admin/orders/[id]/challan?extra=<ec_id>` (prints that consignment's own recipient/parcel/item). The **primary** consignment also takes the same **editable recipient/phone/address/COD/description overrides** (admin_api `_primary_overrides`), fed into both `confirm` and `resubmit_steadfast` — blank fields fall back to the order values.
- **Challan print layout** (`/admin/orders/[id]/challan`, `?extra=` for an additional parcel): **one full A4 page** per parcel (`198×285mm` = A4 minus the 6mm printer margin; `@page { size: A4 portrait }` + `break-after: page` in `globals.css`). Carries Merchant Name (Galada display font, loaded **in that file only** so the 2G storefront never pays for it) + **Merchant ID** (`NEXT_PUBLIC_MERCHANT_ID`, default `F5G6HMWE` — build-time, like every `NEXT_PUBLIC_*`), Parcel ID, mobile, name, item, over the logo watermark. Fragile warning = an inline SVG/CSS plaque (bolted amber sign, hazard triangle, skull-and-crossbones cut out with an SVG `mask`) on a full-bleed black band — **no image asset**, so it prints crisp at any size.
- **Recheck courier history**: `orders/{id}/recheck_fraud/` re-runs `check_phone(order.phone)` and restores `fraud_check_result`; button on the order-detail "Courier delivery history" card.
- **Inline order status**: the Orders **list** has a per-row status dropdown (`set_status`); picking `confirmed` there also fires the Meta Purchase (but does **not** book Steadfast — that stays on the detail-page Confirm).
- **Bulk Steadfast sweep** — "Sync Steadfast (shipped)" button on the Orders list → `POST orders/sync_steadfast/`. Checks **only `status=shipped` orders with a consignment** (earlier states are the admin's call; delivered/cancelled are terminal), refreshes `steadfast_status` on the primary + every `ExtraConsignment`, and sets the order to **`delivered`** (+ status email) when **all** its parcels report `delivered`. Only the exact `delivered` string counts — `partial_delivered` does not; an unbooked extra blocks promotion. Per-order failures are collected and reported, never fatal. Batched `SYNC_BATCH=40` per press (no job queue, each parcel is its own HTTP call) — the response's `remaining` tells the admin to press again. Helper `_sync_order_from_steadfast(order)`; tests `app/tests/test_steadfast_sync.py`.
- **Steadfast webhook (inbound) — they push, we stop polling.** `POST /api/steadfast/webhook/` (`views.steadfast_webhook` → `services/steadfast_webhook.py`). Set in their panel under **Webhook Integration**: Callback Url = that endpoint, **Auth Token(Bearer)** = env `STEADFAST_WEBHOOK_TOKEN` (`COURIER` settings). They send it as `Authorization: Bearer <token>` — that header is the **only** thing between a stranger and marking orders delivered, so it's checked first with `hmac.compare_digest`, and a **blank setting refuses every request** (fail closed, 503). Answers in their documented shape `{"status": "success"|"error", "message"}`; 401 bad token, 404 unknown consignment, 200 for our own bugs (a 500 makes them retry a body that can't succeed).
  - Two notification types. **`delivery_status`** (`consignment_id, invoice, cod_amount, status, delivery_charge, tracking_message, updated_at`) is authoritative: status is lower-cased (their example sends `Delivered`, their docs list `delivered`) onto `Order.steadfast_status` or the matching `ExtraConsignment.status`, then the shared promotion rule runs. **`tracking_update`** (`tracking_message` only) is the hub-by-hub narration — **logged, never allowed to touch a status**.
  - **`ConsignmentEvent`** (append-only) stores every push with its raw payload. This table IS the timeline: the merchant panel's "received at AMBARKHANA / assigned to rider" history exists in **no pollable endpoint**, so it only ever arrives here, once, live. Shown as "Tracking history" on the order detail — per parcel (primary + each extra) — and read-only in Django admin. Identity for dedupe = content + their `updated_at`, so a retry writes nothing and never re-emails; the same message at a new time is a new event.
  - Parcel match is by **consignment id** (invoice is only a fallback: a re-submitted primary gets a fresh `{uid}-HHMMSS` invoice, so an invoice can be stale, an id can't). An unmatched push is still stored with no link, so it's visible instead of vanishing.
  - **`services/consignments.py`** now owns the one promotion rule (`promote_if_all_delivered`, `parcel_statuses`, `normalise_status`), shared by the webhook and the polling sweep so the two can't drift. The sweep **stays** as the backstop — webhooks get missed, and nothing depends on them alone. What the webhook does NOT give: rider name/phone or hub, which Steadfast exposes nowhere but their own dashboard.
  - Needs HTTPS + `STEADFAST_WEBHOOK_TOKEN` set on the server (restart after). Tests: `app/tests/test_steadfast_webhook.py` (19).

## AI salesbot + human handoff  (`app/services/chatbot.py`)
- DeepSeek (`deepseek-chat`), synchronous, **streamed** (per-chunk read timeout; tolerates slow first token). Creds/config in `CHATBOT` settings from env (`DEEPSEEK_API_KEY`, model, timeout, history/token limits).
- **Persona from instructions** stored in DB (`BotConfig`), editable live at **Admin → Bot Instructions** (no restart). Seeded once from `bot_instructions.md`. Persona = **helper/guide, never a salesman** (no pressure, no "buy now", no upselling; hands off when unsure).
- **The DB is the single source of truth for products/prices** (reversed the old "prices only from instructions" rule — that left the bot with only dead `৳{price}` placeholders, so it invented numbers). `_shop_facts()` injects the **whole live catalogue** into the system prompt: every active Product (name, category, price or option range, description, `ProductSpec` rows, out-of-stock flag) + every active PrebuiltCombo (name + category, price, description = authoritative contents, linked customizable items; labelled "READY-MADE LISTINGS" since a one-item listing is not a bundle) + delivery/advance/payment. Rule: quote ONLY these, never invent; unlisted → `[HANDOFF]`.
  - `price_bounds()` returns `(0,0)` for a dupatta with no active options — `_shop_facts` **falls back to `base_price`** so the bot never quotes ৳0; a genuinely unpriced product is flagged `PRICE NOT SET` (no quote, hand off).
  - Combo item **counts are never derived** from the M2M — descriptions list items (e.g. বরমালা, স্ট্যাম্প প্যাড) that aren't separate Products, so a count would contradict the description.
  - The instruction file's `৳{price}` / `{delivery_charge}` are **placeholders nothing substitutes**; `_BEHAVIOR` tells the bot to always use LIVE SHOP DATA instead.
  - `_shop_facts` also injects a **DELIVERY/PAYMENT/CONTACT** block (delivery charge + inside-district rate, advance, COD, **bKash/Nagad numbers**, **contact phones**) and a **BUSINESS INFO** block (address, delivery time, area served, support hours, Facebook/Instagram, how-to-order + custom-order process, privacy/terms links). All from `settings.SHOP` (env-overridable). Hard rule: **never invent a phone/contact/bKash/Nagad number or address** — quote only what's fed, else `[HANDOFF]`. (Fixed a real bug where the bot hallucinated a phone number because none was provided.) Bot answers 24/7 but tells late-night customers a human confirms in the morning (support hours 5am–11pm).
- Control tags parsed out before the customer sees them: `[HANDOFF]` (→ session `waiting_admin`, bot stops) and `[GALLERY: slug]` (→ `resolve_gallery_tags` rewrites to a `{FRONTEND_URL}/gallery/<slug>` link; unknown/blank slug → the `is_bot_default` GalleryTag). `_shop_facts` lists active gallery tag slugs so the bot knows which to send. (Old `[IMAGE]`/`[ALBUM]`/ChatMedia removed.)
- Handoff = **per-chat takeover**: **Admin → Live Chats** (polling, ~4s). Admin reply → session `admin`, bot silenced **for that chat only**; back-to-bot / close. Sidebar badge + sound + browser notification on new waiting chat (poll `/api/admin/chat-unread/`).
- **Images both ways**: `ChatMessage.upload` (Pillow-capped 1600px). Customers attach images in the widget; admins attach in Live Chats. Tap → lightbox (`components/Lightbox.tsx`). Chat uploads auto-purge after 30 days via `purge_old_chat_uploads` (cron).
- Widget: floating pill on storefront (hidden on /admin), quick replies, dedupes optimistic messages by id.

## Meta ads tracking — central CAPI + Pixel  (BUILT)
- Retires the old `webhook.mttasin.com` project; this repo is the single hub. Dataset ID = Pixel ID (Meta merged them).
- **CAPI** (`app/services/capi.py`): SHA-256 hashed PII, `event_id` dedup (`purchase.{uid}`), fbp/fbc capture. `CapiEvent` audit model + `send_pending_capi` management command (cron retry). **Purchase fires on CONFIRM, not at checkout** (COD, Option A): checkout stashes fbp/fbc/source_url/ip/ua on the Order (`meta_*` fields) and fires nothing; `fire_order_purchase(order)` (action_source=website, replaying the stashed match data) runs on any transition **into** `confirmed` — the `confirm` action, `set_status→confirmed`, and the Django-admin confirm — so a cancelled/declined review never reports a conversion. Deduped by event_id, so confirming twice fires once. The **browser Pixel Purchase at checkout was removed** (else Meta would count at checkout regardless). Custom-request fires Lead. ## Caching  (`app/services/cache.py`)
Read-through caches over the hot, rarely-changing reads. All through Django's cache API, so they follow `REDIS_URL` — Redis in prod, LocMem without it.
- **What is cached**: the `/api/home/` payload (five tables + image prefetch, hit by every visitor), `shop-info` (every cart + checkout), the chatbot's **`_shop_facts()`** (the heaviest read in the app — the whole catalogue, rebuilt on *every* message), and **`check_phone()`** per phone (two courier logins + two lookups, sitting inside checkout).
- **Invalidation is a version counter**, not key enumeration: `bump_catalogue()` (from `app/signals.py`, on save/delete of any catalogue model) increments `catalogue:version`, which every catalogue key embeds — one bump orphans every variant (per host, per shape) and the orphans age out by TTL.
- **LocMem is per worker process**, so with no Redis a save in one Passenger worker cannot clear another's copy. That is why every entry also carries a short TTL (`CATALOGUE_TTL` 300s, `FRAUD_TTL` 600s): staleness is bounded by the TTL even with no Redis at all, and Redis just makes invalidation instant.
- **The key is re-evaluated after the build** (`cached()` takes a callable). Building can itself write a catalogue row — `SiteSettings.get_solo()` creates the singleton on first read — bumping the version mid-build; storing under the pre-build key would file the value under a generation nothing ever reads again, i.e. a cache that permanently misses. A test pins this.
- **A miss must be harmless**: everything is recomputable, and a cache backend failure is caught and logged, never raised — 128MB with eviction means any key can vanish.
- The home/shop-info key carries the **request host** (serialized payloads embed absolute media URLs, so dev and prod must not share an entry); the bot key carries a fingerprint of `settings.SHOP` (a delivery-charge change is a different entry, not a stale one).
- **A courier outage is never cached** — caching a transient failure would pin "advance required" on that customer for the whole TTL, turning a blip into a policy. `check_phone(phone, refresh=True)` bypasses the cache; that is what the admin's Recheck button uses.
- Already-existing caches keep their own keys: `services/gallery_cache.py`, and analytics (rate limit, 8s presence, 5min `_known_slugs`).
- **Test isolation**: the cache outlives a test method, so a TestCase that calls the same cached path twice must `cache.clear()` in `setUp` (see `test_fraud_check.AggregateTests`).
- **There is a SECOND cache layer in front of this one**: the storefront's `apiGet()` (`frontend/src/lib/api.ts`) sets `next: { revalidate: 60 }`, so every catalogue read Next.js makes is up to 60s stale (longer in practice — stale-while-revalidate serves the old value while refetching). It predates the Django caching and is **not** invalidated by an admin save. So an edit shows up: instantly in the API, within 60–120s on `/products` and the homepage. Deliberate (2G bandwidth); drop `revalidate` to ~10 if that ever feels slow. `/api/combos/` has no Django cache at all — that page's delay is entirely this layer.
- Tests: `app/tests/test_caching.py` (15).

## Finance cash-book  (BUILT)
Complete money system: every taka in (Steadfast payouts + any other source) and out (ads with VAT, materials, credit purchases, salary…), with P&L over any range. Spec: `docs/superpowers/specs/2026-07-27-finance-cashbook-design.md`. **Replaced per-order `cost_price` entirely.**
- **Cash basis.** Income = money actually received. A Steadfast payout is entered as the **net they sent** — they already deducted the delivery charge and their 1% COD fee, so nothing is recomputed. The variable real delivery charge (175/110/whatever) needs no field; it's already inside the payout.
- **Models** (`models.py` "Finance" block): `FinanceCategory` (one table, `kind=income|expense`; seeded by migration 0033), `Supplier`, `Expense`, `ExpensePayment`, `Buyer`, `Income`, `IncomePayment`. `FinanceAccount` choices = cash/bank/bkash/nagad/card/other.
- **Order links are a MARK ONLY** (`Expense.orders` / `Income.orders` M2M): a note of what the money was for. **No split, no allocation, no per-order profit** — tests assert marking changes no total. Visible from both ends (order detail shows a read-only "Money marked against this order" panel via `finance/order/<id>/`).
- **Fee direction is the load-bearing rule.** `fee_amount` (exact taka, never derived) on every row: on an **Expense/ExpensePayment** it's paid **on top** (`total_out = amount + fee`), on an **Income** it's **deducted** (`net = amount − fee`). Flat charges (NPSB) are just typed; `settings.FINANCE_FEE_RATES` (env `FINANCE_FEE_BKASH` 1.85, `FINANCE_FEE_NAGAD` 1.45) only pre-fills the box via a `%` button. A payment's fee is spent but is **not** credited against the supplier's due.
- **VAT is inside the amount** (`vat_amount` = breakdown, never added on top) — the amount is what actually left the bank. The form's `15%` button extracts VAT from a VAT-inclusive figure.
- **Credit = a RUNNING ACCOUNT per contact, both directions** (owner's call; two separate lists so they can never be confused): purchases on credit = `Supplier` + `Expense.is_credit` → **dues**; sales on credit = `Buyer` + `Income.is_credit` → **receivables**. A **`CreditPayment`** (`kind=payable|receivable` + supplier/buyer FK) comes off the **contact's total balance**, never off one invoice — `balance = sum(credits) − sum(payments)`. Nothing is allocated or marked settled, so **no history is ever rewritten**: the credits and the payments both stay exactly as they happened. A credit entry **must** name its contact (the balance lives there). Balance may go **negative** = they hold an advance for you; it is reported as-is, never clamped.
- **Statement**: `admin/finance/ledger/?direction=&contact=` replays that contact's credits and payments oldest-first with a **running balance** (same-day credit sorts before same-day payment). UI = expand a contact in the Credit tab.
- **Part payment at deal time**: the entry form's credit mode has a *Paid now / Received now* box that writes the first `CreditPayment` automatically (and carries the transfer charge, since that is the money that actually moved). Blank = pure credit deal.
- **A transfer charge never moves a balance** — the counterparty is credited with what they handed over, not with the bank's cut. It is still real cash in `cash_out`/`cash_in`.
- **A credit row carries no `fee_amount` of its own** (nothing moved yet), either side — the serializer rejects it.
- **A credit sale is NOT income until paid** (cash basis): an unpaid credit sale contributes 0 to Income/Net and sits in the buyer's balance; the money enters only through `CreditPayment` rows, on the payment's own date. `sales_total` reports what was sold regardless. 
- **The Credit column is contact-level, never row-level** (`CreditCell`, finance page). A credit row records how the *deal* was made and is never itself "paid off", because a payment comes off the contact's whole balance — so the cell reports where that **contact** stands from `Supplier.due` / `Buyer.receivable`: `on credit · ৳X left` while anything is outstanding, **settled** once the balance is ≤ 0 (a negative balance = they hold an advance, said so in the tooltip). It used to always read "on credit", which looked like an unpaid invoice forever.
- **Numbers shown side by side** so nothing hides: **Income** (cash actually received) · **Sales** (incl. unpaid credit) · **Spending** (`amount+fee` by date) · **Cash out** (non-credit + credit fees + payments) · **Dues** (I owe) · **Receivables** (owed to me) · fees · VAT. Headline **Net = income received − spending**. Dues and receivables are never netted against each other.
- **API** `app/finance_api.py`: viewsets `expenses/ incomes/ suppliers/ buyers/ finance-categories/ credit-payments/` + `finance/summary/?start=&end=`, `finance/meta/` (accounts + default rates), `finance/order-search/` (light typeahead — the admin order serializer is far too heavy), `finance/order/<id>/`. Dashboard card = `month_net()`.
- **Admin UI** `/admin/finance` (nav icon `wallet`), tabs: Overview (range picker, stat cards, in-vs-out bar chart, category pies, both credit panels) · Expenses · Income · **Credit** (*I owe* + *Owed to me*; expand a contact for its statement + running balance, record/edit/delete payments; ignores the date range — what is owed is owed) · Categories (+ suppliers & buyers). Shared `EntryForm` for both sides, shared `CreditSide`/`ContactLedger`/`CreditPaymentForm` for both directions; `OrderPicker` typeahead for marks.
- Tests: `app/tests/test_finance.py` (66) + `frontend/src/lib/financeApi.test.ts` (12).

## Staff & permissions — moderator system  (BUILT)
Staff (moderators) log into the same panel as the owner, but the owner decides **which sections they see** and **whether they can change anything there**. Spec: `docs/superpowers/specs/2026-08-01-moderator-access-control-design.md`; plan: `docs/superpowers/plans/2026-08-01-moderator-access-control.md`.
- **Two identities only.** Owner = `is_superuser` (bypasses every check). Moderator = `is_staff` + a `StaffProfile` row whose `access` JSON maps section → `view` | `full`. **A staff user with no profile has access to nothing** — the safe default, so an account made straight in Django admin inherits no power.
- **17 sections** in one registry, `app/permissions.py` `SECTIONS` (key → label, owner_only). `view` = every GET passes, every write 403s; `full` = everything. `/admin/products` + `/admin/customization` are **one section** (`products`) — same endpoints, splitting them would be a lie.
- **Never grantable (owner only):** Bot Instructions, Site Settings, Staff, Audit Log, and **hard-deleting an order** (a moderator with `orders: full` can cancel, not erase). Finance **is** grantable — just `none` by default.
- **Enforcement** = `SectionPermission` (+ `SectionViewSetMixin` for viewsets, `section_access("key")` permission classes for function views). A view declaring no section is **refused**, so a forgotten one fails closed. `VIEW_WRITES` / `view_writes=True` whitelist the POSTs that aren't edits (`orders.mark_seen` fires on page open, `fraud-check/` is a lookup, `push-subscribe/` registers a device) so a view-only moderator doesn't see a broken page.
- **The load-bearing test** (`app/tests/test_staff_access.py`, 29): walks the URLconf and asserts **every** `/api/admin/` route declares a section, `owner_only`, or `any_staff`. A new endpoint added without a guard fails the suite instead of shipping wide open. It already caught one real hole — the DRF router's own index at `/api/admin/` was public, listing the whole admin surface; it now needs staff.
- **Cross-section reads degrade, they don't explode:** the dashboard returns `shows_money`/`shows_orders` and omits the cash-book figures without `finance:view`; `chat-unread/` (polled from every page) zeroes the counters the caller may not see instead of 403-ing.
- **Django admin (`:8000/admin`) is owner-only** — `admin.site.has_permission` requires `is_superuser`. Without it the whole system is bypassable in one URL, since moderators are `is_staff`, exactly what Django's admin checks.
- **Staff API** `app/staff_api.py` → `admin/staff/` (owner only): create/edit/disable/delete + `set_password/` + `sections/` (the grantable list, so the UI matrix can't drift from the backend). Guards: cannot touch a superuser row, cannot edit yourself, `is_staff=True`/`is_superuser=False` are set server-side (a payload asking for superuser is ignored), owner-only/unknown sections and junk levels rejected. **Deactivating or changing a password deletes that user's `Token`** so the session dies now. Permission changes need no re-login — the level is read from the DB per request. Tests: `app/tests/test_staff_api.py` (18).
- **Audit log** `AdminAuditLog` + `app/middleware.py` (`AdminAuditMiddleware`, last in `MIDDLEWARE`): every non-GET to `/api/admin/` by an authenticated staff user, with who/what/section/status/IP and the request body. Body is captured **before** the view (DRF's parsers consume it — reading after raises `RawPostDataException`), multipart is skipped, `password`/`token`/`secret`/`key` are redacted, payloads truncated to 2000 chars. **Failures are logged too** — a wall of 403s from one account is itself the signal. Noise skipped: `mark_seen`, `push-subscribe`, `login`. Append-only: the API is read-only even for the owner. `purge_audit_log` (cron, `AUDIT_RETENTION_DAYS` 180). Tests: `app/tests/test_audit_log.py` (12).
- **Frontend**: `lib/adminAuth.ts` (`can`/`isReadOnly`/`sectionForPath`/`firstAllowedPath`, 15 tests) + `components/admin/AdminAuthProvider.tsx` (`useAdminAuth`, `useCanWrite`). The sidebar renders only readable sections, the route guard bounces you to `firstAllowedPath`, and a read-only section shows one **View only** banner from the layout (plus disabled write controls on Orders). ## Conventions
- Secrets/config in `backend/.env` (not committed): `SECRET_KEY`, `DEBUG`, `ALLOWED_HOSTS`, `DATABASE_URL`, `CORS_ALLOWED_ORIGINS`, `CSRF_TRUSTED_ORIGINS`, `FRONTEND_URL`, courier creds, Steadfast API keys, `STEADFAST_WEBHOOK_TOKEN` (inbound webhook secret), SMTP, `DEEPSEEK_API_KEY`, bKash/Nagad numbers, `META_*`, delivery (`DELIVERY_CHARGE`, `DELIVERY_CHARGE_INSIDE`, `INSIDE_DISTRICT`, `DELIVERY_TIME`), bot business info (`CONTACT_PHONE`, `WHATSAPP_NUMBER`, `SHOP_ADDRESS`, `SUPPORT_HOURS`, `FACEBOOK_URL`, `INSTAGRAM_URL` — all default to real values), Web Push (`VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`), finance fee pre-fills (`FINANCE_FEE_BKASH`, `FINANCE_FEE_NAGAD`, … — UI defaults only), `AUDIT_RETENTION_DAYS` (180). Password with special chars in `DATABASE_URL` must be **URL-encoded**. Frontend build-time vars live in `frontend/.env.local`: `NEXT_PUBLIC_META_PIXEL_ID`, `NEXT_PUBLIC_MERCHANT_ID`.
- Admin English, customer Bengali.
- After model changes: `python manage.py check` + makemigrations/migrate.
- **Admin-API tests must authenticate as `User.objects.create_superuser(...)`** — a bare `is_staff=True` user now correctly holds *no* sections and every admin call 403s. Testing a moderator is the deliberate exception (give them a `StaffProfile`).
- Frontend tests: **Vitest + React Testing Library**, `npm test` from `frontend/`. The `components/ui/` library is built TDD; add a test with each new component. Build check: `npm run build`.
- New UI: compose from `components/ui/` primitives + `Container`/`Section`; use design tokens (`plum/rose/gold/surface/surface-2/muted/border`), never raw hex; headings use `font-display`.
- Anonymous identity via `X-Cart-Token` header (localStorage), not cookies — avoids cross-origin cookie pain and works for cart + chat.
- Run backend from `backend/` (`../env/Scripts/python manage.py …` on this machine); frontend `npm run dev`.

## Deployment (cPanel + Passenger)  — see `DEPLOY.md`
- Frontend **`zaujain.xyz`** (Node.js App, startup `server.js`), backend **`backzaujain.mttasin.com`** (Python App, `backend/passenger_wsgi.py`), **PostgreSQL** in prod. Frontend + backend are **different registrable domains** — fine because identity is the `X-Cart-Token` header, not cookies. Just set `CORS_ALLOWED_ORIGINS=https://zaujain.xyz`, `ALLOWED_HOSTS=backzaujain.mttasin.com`, `CSRF_TRUSTED_ORIGINS=https://backzaujain.mttasin.com`, `FRONTEND_URL=https://zaujain.xyz`. (Backend can later move to `api.zaujain.xyz` with just env changes + a frontend rebuild.)
- Prod-only **security headers** auto-enable when `DEBUG=False` (settings block): `SECURE_PROXY_SSL_HEADER` (Passenger sends plain HTTP behind HTTPS), SSL redirect, secure session/CSRF cookies, HSTS, nosniff. `manage.py check --deploy` is clean with `DEBUG=False` + a real `SECRET_KEY`.
- Deploy transfer trick (slow upload line): push source zips to Google Drive, pull server-side with `python3 -m gdown "...uc?id=FILE_ID"` (fast server bandwidth) — FTP passive ports are firewalled here. Frontend = **build locally with prod `NEXT_PUBLIC_*` in `.env.local`**, upload only `.next/ public/ package.json package-lock.json server.js next.config.ts` (no `node_modules`/`src`), then `npm install --omit=dev` on the server (avoids build-RAM OOM). DB migrated via pgAdmin **Plain SQL** dump (custom-format `.dump` fails: server pg_restore 16 rejects newer archive) → `DROP SCHEMA public CASCADE; CREATE SCHEMA public;` then `psql -f`.
- Static via **WhiteNoise** (`CompressedStaticFilesStorage`, `collectstatic`); media served by Django `re_path` when `DEBUG=False`. `CSRF_TRUSTED_ORIGINS` + `CORS_ALLOWED_ORIGINS` from env.
- **Backend secrets** → cPanel Python App env vars (or `.env`; cPanel wins), read at runtime → restart after change. **Frontend `NEXT_PUBLIC_*`** bake in at BUILD time → rebuild after change.
- Cron (no job queue): `send_pending_capi` (CAPI retry) + `purge_old_chat_uploads` (30-day chat images) + `purge_orphan_media` (monthly, unreferenced media files) + `purge_audit_log` (monthly, 180-day admin audit trail).
